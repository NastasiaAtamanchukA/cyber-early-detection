# Техническое задание на разработку Cyber Early Detection

## 1. Общие сведения

Система Cyber Early Detection является учебным full-stack прототипом для раннего обнаружения кибератак на основе анализа событий безопасности и ML-оценки риска. Система состоит из frontend-интерфейса, backend API, отдельного ML-сервиса, PostgreSQL и инфраструктуры запуска через Docker Compose.

## 2. Назначение системы

Система предназначена для демонстрации полного цикла обработки события безопасности: прием события, проверка, нормализация, формирование признаков, ML-оценка риска, сохранение в БД, создание алерта и отображение результата в интерфейсе SOC-аналитика.

## 3. Цели разработки

Главная цель - создать проверяемый MVP, который можно запустить, протестировать и защитить по учебному чек-листу. Дополнительная цель - показать архитектурный подход к разделению ingestion, ML scoring, хранения данных и пользовательского интерфейса.

## 4. Функциональные требования

| Код | Название | Описание | Приоритет | Критерий приемки |
| --- | --- | --- | --- | --- |
| FR-01 | Прием события безопасности | Система должна принимать JSON-событие через REST API. В payload должны передаваться timestamp, host, user, event_type, message, source_name, source_kind и metadata. | Must | POST /api/v1/events/ingest возвращает успешный ответ; событие появляется в списке событий. |
| FR-02 | Валидация входного события | Backend должен проверять обязательные поля, типы данных и корректность структуры события. | Must | При некорректном payload API возвращает ошибку валидации; валидное событие проходит дальше. |
| FR-03 | Нормализация события | Событие должно приводиться к единой внутренней структуре, пригодной для хранения и анализа. | Must | В БД сохраняются исходное сообщение, нормализованные поля, источник, пользователь, хост и тип события. |
| FR-04 | Формирование признаков | Backend должен сформировать feature vector для ML-сервиса на основе нормализованного события. | Must | ML-сервис получает структурированный набор признаков, а не только сырой текст. |
| FR-05 | ML-оценка риска | ML-сервис должен рассчитывать risk_score/anomaly_score для события. | Must | Ответ /predict содержит числовой score и признак аномальности/уровень риска. |
| FR-06 | Создание алерта | Если риск превышает заданный порог, backend должен создать alert. | Must | В таблице/списке алертов появляется запись с severity, title, status и связью с event. |
| FR-07 | Связь с инцидентом | Алерт должен быть связан с инцидентом либо создавать новый инцидент в рамках упрощенной логики. | Should | В карточке alert видна связь с incident или создается новый incident по событию. |
| FR-08 | Просмотр событий | SOC-аналитик должен видеть список событий и базовые поля события. | Must | GET /api/v1/events и UI возвращают/показывают события. |
| FR-09 | Просмотр карточки события | SOC-аналитик должен открывать детальную карточку события. | Must | GET /api/v1/events/{id} возвращает timestamp, host, user, event_type, message, risk_score. |
| FR-10 | Просмотр алертов | SOC-аналитик должен видеть список алертов с критичностью. | Must | GET /api/v1/alerts и UI показывают severity/status/title. |
| FR-11 | Healthcheck backend | Backend должен иметь endpoint проверки состояния. | Must | GET /api/v1/health возвращает ok/healthy. |
| FR-12 | Healthcheck ML | ML-сервис должен иметь endpoint проверки состояния. | Must | GET /health возвращает ok/healthy. |
| FR-13 | Swagger/OpenAPI | Backend должен предоставлять интерактивную документацию API. | Should | /docs открывается и содержит основные endpoints. |
| FR-14 | Демо-данные | Проект должен позволять быстро добавить тестовые события. | Should | scripts/seed_demo.sh или curl-пример создают события для демонстрации. |
| FR-15 | Контейнерный запуск | Система должна запускаться набором контейнеров. | Must | docker compose up --build -d поднимает frontend, backend, ML и БД. |
| FR-16 | CI/CD | В репозитории должен быть workflow для проверки кода. | Must | GitHub Actions запускает backend lint/test, ML tests, frontend build и Docker build. |
| FR-17 | Автотесты | В проекте должны быть минимум 5 unit/integration/api тестов. | Must | pytest/npm проверки выполняются в CI без падения. |
| FR-18 | Статический анализ | Backend/ML код должен проходить линтер. | Should | ruff или аналогичный инструмент выполняется в CI. |

## 6. Архитектура системы

Архитектура включает следующие компоненты: React frontend, FastAPI backend, FastAPI ML service, PostgreSQL, Docker Compose и GitHub Actions. Frontend обращается к backend по REST API. Backend отвечает за бизнес-логику, валидацию, нормализацию, сохранение и вызов ML-сервиса. ML-сервис инкапсулирует модель оценки риска. PostgreSQL хранит источники, события, алерты, инциденты и служебные сущности.

## 7. API-интерфейсы

| Метод | Endpoint | Назначение | Вход | Выход |
| --- | --- | --- | --- | --- |
| POST | /api/v1/events/ingest | Прием события безопасности | JSON event payload | Event + calculated risk / alert creation |
| GET | /api/v1/events | Получение списка событий | query/filter параметры при необходимости | Список событий |
| GET | /api/v1/events/{id} | Получение карточки события | event_id | Детальная информация по событию |
| GET | /api/v1/alerts | Получение списка алертов | query/filter параметры при необходимости | Список алертов |
| GET | /api/v1/alerts/{id} | Получение карточки алерта | alert_id | Детальная информация по алерту |
| GET | /api/v1/health | Проверка backend | нет | Статус backend |
| GET | /health | Проверка ML-сервиса | нет | Статус ML-сервиса |
| POST | /predict | Расчет риска ML-сервисом | feature vector | risk_score/anomaly_score |

## 8. Модель данных

| Сущность | Назначение | Ключевые поля | Комментарий |
| --- | --- | --- | --- |
| LogSource | Источник логов | id, name, kind, description, created_at | Описывает, откуда пришло событие: ssh-gateway, windows-agent, nginx, sysmon и т.п. |
| Event | Событие безопасности | id, source_id, timestamp, host, user, event_type, message, metadata, risk_score, is_anomaly | Центральная сущность. Хранит нормализованное событие и результат оценки риска. |
| Alert | Алерт | id, event_id, incident_id, title, severity, status, created_at | Создается при превышении порога риска или при подозрительном событии. |
| Incident | Инцидент | id, title, severity, status, affected_host, affected_user, first_seen, last_seen | Группирует алерты в расследуемую сущность. |
| CollectionSchedule | Расписание сбора | id, code, name, interval_label, enabled | Описывает демонстрационную/плановую настройку сбора событий. |
| CollectionRun | Запуск сбора | id, schedule_id, status, events_created, alerts_created | Фиксирует результат отдельного запуска сбора/seed-сценария. |

## 9. Требования к безопасности

Секреты не должны храниться в репозитории. Для локального запуска используется `.env`, в репозитории хранится только `.env.example`. В промышленной версии необходимо добавить HTTPS, RBAC, журналирование действий пользователей, ограничение сетевого доступа к БД и ML-сервису, управление секретами через CI/CD secrets или vault.

## 10. Требования к тестированию

Минимальный набор автотестов должен покрывать backend health, ML health, прием события, получение списка событий/алертов и расчет ML score. Ручное тестирование должно включать не менее трех сценариев: запуск проекта, отправка нормального события, отправка подозрительного события и просмотр результата в интерфейсе.

## 11. Требования к CI/CD

GitHub Actions должен запускаться при push/pull request в main/dev. Pipeline должен включать backend lint/test, ML tests, frontend build и Docker build. Для закрытия чек-листа требуется именно успешный последний прогон, а не просто наличие workflow-файла.

## 13. Ограничения и дальнейшее развитие

Текущий проект является учебным MVP. Для production-уровня необходимо добавить RBAC, HTTPS, очередь событий, расширенные парсеры Sysmon/auditd/nginx, корреляционные правила, мониторинг Prometheus/Grafana, резервное копирование БД, аудит действий пользователей и устойчивую стратегию обучения/обновления ML-модели.
