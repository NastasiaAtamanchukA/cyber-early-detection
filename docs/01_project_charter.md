# Устав проекта

## 1. Паспорт проекта

**Наименование:** Cyber Early Detection.  
**Тип:** учебный full-stack проект с элементами ML и SOC-мониторинга.  
**Репозиторий:** https://github.com/NastasiaAtamanchukA/cyber-early-detection.  
**Развернутое приложение:** https://cyber-early-detection.ru/.  
**Дата подготовки документации:** 25.05.2026.  
**Статус:** MVP / демонстрационный прототип для защиты учебного проекта.


## 2. Инициатор и основание проекта

Проект выполняется в рамках учебной проверки, где требуется показать не только программную реализацию, но и полный набор проектных артефактов: устав, техническое задание, план управления, RACI, реестр рисков, user stories, backlog, UML/ER-диаграммы, CI/CD, тесты, deployment guide, release notes и презентацию. Основанием для завершения проекта является итоговый чек-лист преподавателя и фактическая работоспособность прототипа.


## 3. Проблема, которую решает проект

В реальной инфраструктуре события безопасности поступают из разных источников: системных журналов, сетевых сервисов, приложений, средств защиты, Linux/Windows-хостов. Даже в учебном масштабе поток таких событий быстро становится неудобным для ручной проверки. Отдельное событие само по себе может выглядеть неопасным, но совокупность признаков - тип события, пользователь, хост, частота, текст сообщения, источник и технический контекст - может указывать на раннюю стадию атаки. Проект демонстрирует подход, при котором события автоматически нормализуются, оцениваются по уровню риска и передаются аналитику уже в виде приоритизированных алертов.


## 4. Цель проекта

Цель проекта - разработать и продемонстрировать работающий прототип системы раннего обнаружения кибератак, который принимает события безопасности через API, приводит их к единому формату, рассчитывает риск с помощью ML-сервиса, сохраняет результат в базе данных и отображает события, алерты и инциденты в веб-интерфейсе SOC-аналитика.


## 5. Измеримые задачи проекта

1. Реализовать backend API для приема, просмотра и детализации событий безопасности.  
2. Реализовать нормализацию входных событий в единую модель данных.  
3. Реализовать отдельный ML-сервис для расчета risk score/anomaly score.  
4. Сохранить события, алерты, инциденты и источники логов в PostgreSQL.  
5. Реализовать frontend-интерфейс для просмотра событий и алертов.  
6. Обеспечить запуск проекта через Docker Compose.  
7. Добавить автотесты, статический анализ и CI/CD pipeline.  
8. Подготовить документы и диаграммы, закрывающие чек-лист преподавателя.  
9. Подготовить release notes и GitHub Release `v0.1.0`.  
10. Подготовить сценарий демонстрации для защиты.


## 6. Бизнес-ценность и учебная ценность

Бизнес-ценность прототипа состоит в демонстрации подхода к сокращению времени первичного обнаружения подозрительных событий: аналитик видит не сырой поток логов, а нормализованные события с рассчитанным риском и алертами. Учебная ценность состоит в том, что проект показывает полный цикл разработки современной системы: API, БД, ML-сервис, frontend, контейнеризация, CI/CD, тестирование, документация, UML/ER-моделирование и релизный процесс.


## 7. Границы проекта

В проект входит: прием JSON-событий, нормализация, хранение в БД, расчет риска через ML-сервис, создание алертов, базовая модель инцидентов, frontend для просмотра данных, Docker Compose, CI/CD, тесты, документация и диаграммы.  

В проект не входит: промышленная SIEM-корреляция, полноценный RBAC, SSO, HTTPS-терминация, промышленная очередь событий, кластеризация, long-term storage, полноценный SOC workflow, интеграция с реальными EDR/SIEM, production monitoring, multi-tenant режим и сертифицированная защита информации.


## 8. Заинтересованные стороны

**Студент / команда:** разрабатывает, документирует и защищает проект.  
**Преподаватель / проверяющий:** оценивает соответствие чек-листу и демонстрацию.  
**SOC-аналитик как целевой пользователь:** использует интерфейс для просмотра событий, алертов и инцидентов.  
**Администратор системы:** запускает стенд, проверяет healthcheck, добавляет тестовые события.  
**Разработчик:** поддерживает код, тесты, CI/CD и документацию.


## 9. Основные пользователи и роли

В учебной версии роли реализованы скорее логически, чем как полноценный RBAC. SOC-аналитик просматривает события, алерты и инциденты. Администратор запускает проект, проверяет состояние сервисов и отправляет тестовые события. Разработчик работает с кодом, тестами, миграциями и CI/CD. Проверяющий открывает сайт, GitHub, документацию, презентацию, релиз и последний workflow run.


## 10. Ключевые результаты проекта

1. Публичный GitHub-репозиторий с исходным кодом.  
2. Развернутое приложение или инструкция запуска в один шаг.  
3. Backend API с документацией Swagger.  
4. ML-сервис для оценки риска.  
5. Frontend-интерфейс SOC-аналитика.  
6. PostgreSQL-модель данных.  
7. Docker Compose для локального запуска.  
8. CI/CD pipeline.  
9. Набор автотестов и ручных тестовых сценариев.  
10. Полный пакет проектной документации и схем.  
11. Презентация защиты.  
12. GitHub Release `v0.1.0` с release notes.


## 11. Критерии успеха

Проект считается успешно завершенным, если: репозиторий доступен; README описывает запуск и основные API; проект поднимается через Docker Compose; backend и ML healthcheck возвращают успешный статус; тестовое событие принимается через API; риск рассчитывается ML-сервисом; frontend отображает события и алерты; CI/CD workflow проходит без ошибок; существует релизный тег `v0.1.0`; документация и схемы закрывают все пункты чек-листа.


## 12. Ограничения

Проект является MVP и учебным прототипом. Он не должен рассматриваться как готовая промышленная SIEM/UEBA-система. В текущих границах допустимы упрощения: фиксированная схема событий, ограниченное число источников логов, демонстрационная ML-модель, отсутствие многоуровневой ролевой модели и отсутствие production-grade наблюдаемости.


## 13. Допущения

Предполагается, что проверка выполняется по учебному чек-листу, а не по требованиям промышленной эксплуатации. Предполагается наличие Docker и Docker Compose у проверяющего при локальном запуске. Предполагается, что демонстрационные данные достаточно репрезентативны для показа логики event -> risk score -> alert -> incident. Предполагается, что внешняя доступность сайта может быть временно заменена локальным запуском по Deployment Guide.


## 14. Верхнеуровневые риски

Критичные риски проекта: падающая CI/CD-сборка, отсутствие зеленого workflow run, недостаточное число тестов, отсутствие GitHub Release, недоступность сайта во время проверки, ошибки запуска Docker Compose, неполная документация, недостаточная детализация диаграмм. Для каждого риска подготовлены меры снижения в реестре рисков.


## 15. Вехи и завершение проекта

Финальная веха проекта - релиз `v0.1.0`. Перед созданием релиза необходимо добавить документацию в репозиторий, исправить CI/CD, выполнить тесты, проверить сайт или локальный запуск, подготовить release notes и приложить ссылку на зеленый workflow run. После этого проект можно считать готовым к защите.
